**Evidence available:** TypeScript check (`tsc --noEmit`), Vitest suite (80 unit & regression tests passed, 11 skipped), and production build (`vite build` + esbuild) have passed with zero errors. All Phase 1 requirements, code review corrections, and final closure checks have been completed:
1. **Critical dev auth security, isolation & loopback binding:** Client-controlled privilege assignment and arbitrary identity parameters completely removed from `auth.standaloneLogin`. Replaced with strictly server-controlled test personas (`customer`, `vendor`, `rider`, `admin`). Disabled by default (`MTM_ENABLE_DEV_AUTH=1`), requires strictly local database host separation and allowlisted DB names (`mtm_dev_*`, `mtm_local_*`, `mtm_test_*`, `mtm_e2e_*`), enforces non-spoofable socket loopback IP verification, rejects cloud environments (`VERCEL`, `RENDER`, `RAILWAY`, etc.), rejects public tunnels (`ngrok-trace-id`, `cf-ray`, `localtunnel-id`), rejects external proxy forwarding headers (`x-forwarded-for`/`x-forwarded-host`/`x-real-ip`), and `resolveServerListenConfig` in `server/_core/index.ts` binds HTTP server strictly to `127.0.0.1`, failing closed if external binding (`HOST=0.0.0.0`), production, or cloud hosting is detected.
2. **Fulfillment-type-aware transitions & rider protection:** Server-enforced state machine in `domain.ts` and `routers.ts`: Pickup `placed → accepted → preparing → ready → delivered`; Delivery `placed → accepted → preparing → ready → out_for_delivery → delivered`. Rejects pickup `ready → out_for_delivery`, rejects delivery `ready → delivered` without dispatch, and rejects duplicate delivery completion. Vendor fulfillment operations (`out_for_delivery`, `delivered`, and `failed_delivery`) are strictly prohibited when an active platform rider controls the delivery (`assertNoActiveRiderAssignment`), while preserving rider and administrator authority and audit overrides.
3. **Unified failed-delivery financial handling:** Transactional business service `executeFailedDeliveryTransition` unified across vendor, rider, and administrator actors. For orders with no collected payment: voids outstanding payment record, reverses pending financial ledger entries, preserves inventory in transit without premature restocking, updates delivery assignment status to failed, and writes auditable timeline + audit events. If cash was already recorded or collected, silent voiding is prohibited and throws a CONFLICT error requiring an authorized refund/reconciliation workflow.
4. **Quantity-accurate return recovery workflow with missing quantities:** Delivery failure preserves inventory until physical return and inspection. Additive migration `0006_failed_delivery_recovery.sql` adds `returnReceivedAt`, `returnCondition`, and `returnNotes` to `orders`. Additive migration `0007_order_items_return_quantities.sql` adds `restockedQuantity` and `damagedQuantity` to `order_items`. Additive migration `0008_order_items_missing_quantity.sql` adds `missingQuantity` to `order_items`. All migrations are registered in Drizzle migration journal and snapshots. Transactional business service `executeReturnRecovery` validates each line item, enforces non-negative integers, ensures `restockedQuantity + damagedQuantity + missingQuantity === orderedQuantity`, restores stock only for restocked units, records disposition condition (`restocked`, `partial_loss`, `damaged_shrinkage`, `total_missing`), and prevents duplicate or double-restocking attempts. Client UI in `WorkspacePages.tsx` provides item-level restocked, damaged, and missing quantity controls.
5. **Integration-test database protection:** Dedicated `integration-guard.ts` parses connection URL with strict protocol, host (`localhost`, `127.0.0.1`, `::1`), and database prefix (`mtm_e2e_`) checks. Substring matches across the entire URL are eliminated. Fail-closed default halts execution if unsafe.
6. **API-level regression test suite:** 80 passing tests verify seller delivery, active rider conflict protection on dispatch/completion/failure, fulfillment-type boundaries, handover lockout, duplicate completion prevention, unified failed-delivery across all actors, cash void prohibition, quantity-accurate return recovery (including restocked, damaged, and missing combinations), loopback binding enforcement, allowlisted local DB names, cloud environment rejection, tunnel header rejection, and proxy anti-spoofing isolation. No fake credentials were created. No external publication, remote Git push, or paid-provider activation has been performed.

## 1. Customer identity, profile, location and account controls — In progress; phone OTP blocked
- Customer onboarding includes mobile number login with OTP, name/basic profile, location permission with manual location as an alternative, town, locality and delivery address; customers outside supported delivery areas receive an appropriate service-unavailable message.
- Customers can save multiple addresses. Customer addresses and phone numbers are protected; request only necessary mobile permissions; use INR and Indian address formatting.
- No mock authentication in production, no hardcoded admin password, and no private credentials in frontend code. Include privacy policy and account deletion workflow before public launch.
- **Available now:** real Manus OAuth/session authentication, verified owner-email administrator bootstrap, standalone/pilot authentication fallback for dev/testing, persistent customer contact/profile/address records, address/town/zone checks, and role guards. **Blocked/incomplete:** no SMS OTP provider is connected; do not display or accept an invented OTP as real authentication. Account deletion, privacy/consent and full phone-verification workflow remain public-launch gates.

## 2. Marketplace discovery, categories, storefronts and products — In progress
- Customer home provides address selector, prominent search, promotional banner carousel, configurable shopping categories, nearby and featured merchants, popular products, daily essentials, offers and recently ordered products. Interface is original, polished, fast, mobile-first, low-data, accessible, suitable for affordable Android smartphones, English first with a configurable foundation for Hindi.
- Categories include grocery/kirana, fresh vegetables, fruits, dairy, bakery/snacks, household essentials, personal care, stationery, clothing/footwear, hardware/electrical, home/kitchen and other local shops; admin can add categories without code changes. Regulated categories such as prescription medicines stay disabled until licensing, verification and compliance workflows exist.
- Customers browse shops by category and locality and see only shops able to serve their selected location. Each storefront shows name/logo, cover, description, address, open/closed state, delivery availability/charge, estimated preparation and delivery window, minimum order, categories and products with prices/images.
- Product detail shows images, name, selling price, optional MRP/discount, unit and quantity selector, description, availability, shop name and add-to-cart action. Support pieces, kilograms, grams, litres, millilitres, packets, boxes and dozens; vegetables support 250 g, 500 g, 1 kg and 2 kg; loose goods support price per unit.
- **Available now:** selected-town/locality discovery, secure whitelisted public shop/product DTOs, category/location search, open/unavailable guards, product image upload to durable storage, and fictional demo catalog imagery. **Incomplete:** full promotions/offers/recent-order surfaces, Hindi UI, vendor storefront image upload UX, push updates, product variation system and exact customer location-permission flow.

## 3. Cart, checkout, payments and order integrity — In progress
- First release supports exactly one merchant per checkout. Customers can browse several shops, but products from different shops require separate orders; explain this when they try to mix shops.
- Server-calculated totals transparently include item subtotal, item discounts, delivery charge, any applicable platform fee, configured applicable tax and final amount. Checkout includes saved/new address, contact number, delivery or self-pickup, order notes, substitution preference, payment method and final price review.
- Initial launch supports Cash on Delivery and Cash on Pickup. Manual UPI is enabled only if payment verification is safely implemented. Never mark online payment paid merely because a customer pressed a button or supplied an unverified screenshot; prepare architecture for a verified Indian gateway without claiming it is connected.
- Prevent duplicate orders from repeated checkout taps; prevent negative stock under concurrent ordering; snapshot product prices and fees in placed orders; validate prices/totals on the server; adjust/restock correctly for eligible cancellations.
- **Available now:** one-shop cart, clear shop-change behaviour, selected-zone address validation, delivery/pickup, customer review of integer-paise totals, server fee/commission computation, idempotent retries (including concurrent retries), stock reservation, price/fee/address snapshots, COD/cash-pickup records, cancellation rules, and audit/ledger entries. **Incomplete:** configurable tax/discount campaigns, verified online payment gateway, manual UPI and coupon redemption.

## 4. Customer orders and service — In progress
- Order states: Placed → Accepted → Preparing → Ready for Pickup → Out for Delivery → Delivered, plus Rejected, Cancelled and Failed Delivery with appropriate rules. Show clear timeline and status notifications; do not simulate GPS tracking.
- Customer can view previous orders, reorder, favorite shops, manage addresses, cancel subject to store policy, request help/support, review shops/products after completed purchases, and receive order-update notifications.
- **Available now:** owner-scoped order detail/timeline, cancellation within allowed states, reorder from current availability/prices, customer-only 8-digit order handover code, and code suppression after five failed attempts until an audited admin reset. **Incomplete:** favorites, reviews, support ticketing and real-time push/SMS notifications. Status refresh is not live GPS tracking.

## 5. Merchant registration, storefront and catalog operations — In progress
- Vendor registration collects owner name, mobile, shop name/category/address/map location/business description/shop images or logo/opening and closing times and relevant business verification details. New merchants require admin approval before selling.
- Vendor dashboard shows today's orders, pending orders, today's sales, total completed orders, products listed, low-stock products and store online/offline status.
- Vendors can add products and phone-uploaded images; set prices, units/variations and stock; edit, delete/archive and temporarily mark products unavailable; create product categories; and add multiple products quickly. Quick entry requires only product name, price and unit; other details are optional.
- Vendor order actions: accept or reject with reason; view items/customer instructions; prepare; mark ready; update item availability with customer approval where necessary; hand order to customer or assigned rider; view order history. Correct merchant is notified; action buttons are clear.
- Vendor delivery settings include self-delivery, platform delivery if available and pickup; service radius, preparation time, minimum order, rule-compliant delivery fee, opening hours and temporarily closed status. Never promise service where delivery is unsupported.
- **Available now:** vendor application + admin approval, shop/catalogue, stock/availability/price editing, order acceptance/preparation/dispatch, seller-managed delivery handover with customer 8-digit code verification and cash recording, delivery failure reporting with reason capture, pickup fulfillment, delivery/pickup settings, owner-scoped uploaded product photos, and customer details visible only for the vendor's own orders. **Incomplete:** Apna Galla integration connector, vendor business-document verification, storefront photo/logo upload UX polish, map pin, radius rule set, customer-approved substitutions, native push notifications, bulk catalog entry and comprehensive earnings/statements panel.

## 6. Vendor earnings, platform fees and financial records — In progress
- Show gross sales, platform commissions, delivery-related charges, refunds/adjustments, amount owed to vendor, settlement and payout history. Never invent completed settlements; record actual payment/settlement events.
- MVP monetization is configurable commission on successfully completed merchant sales and configurable delivery fees. All charges are transparent, calculated correctly and recorded. Subscriptions and sponsored listings remain future capabilities.
- Store auditable order/payment events and immutable order price/fee snapshots. Platform reports use real stored records, not fabricated metrics.
- **Available now:** per-vendor/platform fee terms, price/commission snapshots, transactional fee ledger, collector-reported cash amount and notes, and admin exact-amount reconciliation with audit trail. **Incomplete:** vendor-facing detailed earnings/payout history, refund settlement tooling, payout execution, vendor statements and a complete pending-settlement workflow. No settlement is reported as paid without a settlement event.

## 7. Rider workflow and delivery administration — In progress
- Riders register and require admin approval; can go online/offline, view available/assigned deliveries, accept/decline where allowed, see pickup-shop/customer delivery address, call merchant/customer, open directions in a maps app, mark arrival, confirm pickup and confirm delivery by delivery OTP or other approved proof; view completed deliveries, earnings and cash collection obligations.
- MVP supports admin manual assignment; automatic matching is deferred. Include failed-delivery/customer-unavailable workflow and cash reconciliation. Do not claim live GPS if actual rider updates are unavailable.
- **Available now:** rider registration/admin approval, online status, manual assignment, active-assignment-only contact/address details, Maps directions links, pickup/delivery state transitions, customer code check, reported cash amount, and failed-delivery reason capture. **Incomplete:** SMS OTP delivery, earnings/payouts, automatic assignment, real GPS tracking and a full customer-unavailable recovery/reschedule workflow.

## 8. Admin dashboard and marketplace control — In progress
- Responsive admin dashboard reports real registered customers, active/pending vendors, orders today, GMV, commission revenue, delivery fee collections, pending deliveries, cancellations and pending merchant settlements.
- Admin reviews/approves/rejects/suspends vendors; edits vendor details/storefront visibility/commission; views vendor sales/performance; handles complaints. Admin views customer accounts/order history/support and may suspend fraudulent users with an audit trail.
- Admin searches and filters orders by merchant/status, views order timelines, assigns riders, handles cancellations, records/reviews refunds and resolves disputes. Admin registers/verifies riders, assigns and monitors deliveries, manages cash collections and configures delivery zones/fees.
- Admin settings persist in the database and affect the live application: towns/cities, operational zones and availability, categories, promotional banners, commissions, delivery and platform fees, service areas, minimum-order settings, support contact and discount campaigns.
- **Available now:** actual-count dashboard, vendor/rider approvals, categorized merchant/order queues, order details/timeline, manual rider assignment, town/zone/category creation/activation, vendor fee terms, cash queue/reconciliation, cancellation/rejection, and handover-code recovery. **Incomplete:** customer suspension/admin account tools, complaint/support/dispute/refund case management, settlement dashboards, configurable banners/campaigns/support contact, full per-vendor reporting, and some cross-filter/report views.

- Separate customer/vendor/rider/admin permissions; a vendor cannot access another vendor's private orders or earnings. Protect addresses/phone numbers. Use server-owned role, ownership, price, stock and status checks. Record administrative/suspension changes with audit history.
- Use a maintainable, affordable frontend/backend architecture, persistent relational/transactional database, secure authentication, role-based authorization, image upload/storage, reliable state transitions, stock transaction handling, order/payment audit records, notification infrastructure and environment-based configuration.
- **Available now:** town/zone schema and admin activation controls, mandatory town/locality scope for public discovery and checkout, server-whitelisted DTOs, protected mutations, vendor/rider ownership checks, active-area address checks, stored audit trails, private server-side image uploads, and integration evidence. **Incomplete:** city-specific campaigns/rates beyond current terms, notification delivery infrastructure, full account suspension/audit controls and formal production security review.
